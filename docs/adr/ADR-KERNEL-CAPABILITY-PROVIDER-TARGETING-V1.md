# ADR: Kernel Capability Provider Targeting v1

Статус: accepted
Change: `C-KERNEL-CAPABILITY-PROVIDER-TARGETING-20260905`
Рубеж: M0.3 / M0.4 — Kernel Capability Routing & Multi-Installation Addressing

## Контекст и проблема

В Worldline все продуктовые возможности предоставляются плагинами. Модель плагинов поддерживает множественные инсталляции одного `PluginDefinition` (`multi-install cardinality`) с изолированной конфигурацией и хранилищем состояния для каждой инсталляции (`InstallationId`).

Во время анализа реализуемости и раннего feasibility gate (T-001) среза search providers (`C-BROWSER-SEARCH-PROVIDERS-20260904`) был выявлен фундаментальный архитектурный пробел в `worldline-kernel`:
1. `discover_capabilities_for` корректно обнаруживает все активные инсталляции одного capability.
2. Однако вызов через `CapabilityRegistry::resolve` и `InvocationBroker::invoke` не принимал целевую инсталляцию и всегда детерминированно выбирал кандидата по фиксированному правилу сортировки: highest compatible minor version -> lowest installation ID -> lowest runtime ID.
3. В результате, при наличии двух одновременно активных инсталляций одного контракта (например, `browser.search/0.1`), инсталляция с лексикографически большим `InstallationId` оказывалась навсегда затенённой и недостижимой для вызовов без остановки или удаления первой инсталляции.

Добавление специфичных для поиска роутеров или хранение таблиц предпочтений поисковых систем внутри ядра нарушило бы фундаментальный инвариант Worldline: микроядро не содержит доменной политики браузера, поиска, UI или моделей. Требовался универсальный, минимальный и нейтральный примитив адресации в микроядре.

## Решение: CapabilityTarget и явная адресация по InstallationId

В микроядро добавлен универсальный механизм адресации провайдеров через перечисление `CapabilityTarget`:

```rust
#[derive(Clone, Debug, Eq, Hash, Ord, PartialEq, PartialOrd)]
pub enum CapabilityTarget {
    /// Выбор любого совместимого активного провайдера по детерминированному порядку.
    AnyCompatible,
    /// Явный таргетинг провайдера, опубликованного указанной инсталляцией.
    Installation(InstallationId),
}
```

### Принципы проектирования

1. **Таргетинг привязывается к долговечному `InstallationId`, а не к эфемерному `RuntimeId`**:
   `RuntimeId` уничтожается и пересоздаётся при любом перезапуске, сбое или обновлении плагина. Вызывающая сторона адресует логическую сущность — инсталляцию. Брокер в момент admission разрешает целевой `InstallationId` в текущий живой `RuntimeId`.

2. **Никаких таблиц предпочтений в микроядре**:
   Ядро предоставляет строго механизм («вызови capability X на инсталляции Y»). Выбор предпочтений пользователя, сохранение настроек по умолчанию и профилирование принадлежат внешним слоям (Shell, Workspace, Browser Services).

3. **Строгая семантика отказа: fail-closed без silent fallback**:
   Если целевая инсталляция отсутствует, остановлена, находится в карантине, деактивируется или несовместима по мажорной версии, вызов немедленно завершается типизированной ошибкой `CapabilityError::TargetUnavailable`. Никакого неявного падения на дефолтного провайдера не допускается — тихий fallback нарушил бы ожидания вызывающего и создал бы уязвимость подмены контекста (confused deputy).

4. **Таргетинг не предоставляет полномочий**:
   Указание конкретной инсталляции не обходит и не ослабляет проверки безопасности. Вызывающий обязан обладать валидным capability grant на вызываемый контракт и операцию в момент admission.

5. **Обратная совместимость**:
   Существующий API `kernel.capability_for(caller, capability)` эквивалентен вызову с таргетом `CapabilityTarget::AnyCompatible` и сохраняет прежнюю детерминированную семантику разрешения. Для явной адресации предоставляются `kernel.capability_for_installation(caller, capability, installation_id)` и `context.capability_for_installation(capability, installation_id)`.

## Lifecycle и изоляция RuntimeId

Когда плагин перезапускается супервизором runtime-v1 (например, после сбоя):
- Создаётся совершенно новый `RuntimeId`.
- Предыдущие live authority, security grants и ephemeral state lease уничтожаются.
- Последующие вызовы через хэндл, таргетированный на `InstallationId`, прозрачно резолвят новый `RuntimeId`.
- Полномочия старого рантайма никогда не наследуются новым рантаймом.

## Безопасность и аудит

- Admission time check: проверка прав вызывающего выполняется до резолвинга и вызова сервиса.
- Траекторные события безопасности (`TrajectoryEventKind::RpcCompleted`) фиксируют:
  - Идентификатор запроса (`RpcRequestId`) и вызова (`InvocationId`).
  - Вызываемый capability и запрошенный целевой `InstallationId`.
  - Фактически разрешённый `RuntimeId` (если провайдер был найден).
  - Итоговый класс результата (`RpcOutcomeClass`).
- Тела запросов и ответов (`payload`) не логируются в событиях безопасности и диагностики.

## Отклонённые альтернативы

1. **Таблица preferred-провайдеров внутри ядра (`kernel.set_preferred_provider`)**:
   Отклонено. Выбор дефолтного провайдера — это пользовательская политика и доменная логика, которой нет места в микроядре.
2. **Адресация напрямую по `RuntimeId`**:
   Отклонено. `RuntimeId` эфемерен и перестаёт существовать при первом же рестарте плагина.
3. **Silent fallback на первого доступного провайдера при недоступности целевого**:
   Отклонено. Скрытая подмена провайдера опасна с точки зрения целостности и безопасности.
4. **Промежуточный роутер-плагин в userland без поддержки ядра**:
   Отклонено. Роутер всё равно столкнулся бы с тем, что ядро не даёт вызвать вторую активную инсталляцию того же типа, либо потребовал бы костылей в виде искусственных уникальных имён контрактов для каждой инсталляции.

## Верификация

- Модульные тесты `CapabilityTarget` и `CapabilityRegistry` в `crates/worldline-kernel/src/capability.rs`.
- Acceptance тесты в `crates/worldline-kernel/tests/runtime_v1_acceptance.rs`:
  - Независимый вызов двух активных инсталляций одного контракта.
  - Рестарт инсталляции с получением нового `RuntimeId` без наследования прав.
  - Строгий fail-closed при отсутствии, остановке, карантине или несовместимости инсталляции.
  - Проверка capability-авторизации у вызывающего.
- Все существующие сьюты регрессии и архитектурных инвариантов (`Invoke-WorldlineCi.ps1`, `Test-WorldlineArchitecture.ps1`).
